# Post-H Guardrail Pack
**HC-OS V1 — Milestone H Closed / Enforcement Pack**

This pack combines three layers:
1. **Enforcement Dashboard** — daily operational observation
2. **Lumen Guardrail Constitution** — visibility detection protocol
3. **OctopusMind Guardrail Constitution** — boundary protection protocol

Use them as different control layers:
- **Dashboard** = daily sampling and drift detection
- **Lumen** = detect presence, noticeability, removability
- **OctopusMind** = prevent justification, threshold drift, and strategic reopening

---

# Part I — Post-H Enforcement Dashboard
**HC-OS V1 — Milestone H Protection Mode**

**Owners:** Tree (control) + Lumen (observation)  
**Duration:** 14 days  
**Mode:** No-change / observe → detect → rollback

## 0. Dashboard Purpose
This dashboard exists to answer one question:

**Is H staying invisible and rare over real usage?**

It does **not** exist to measure:
- whether H is good
- whether H is helpful
- whether H can be improved

It exists only to determine whether H remains **restrained and stable over time**.

## 1. Daily Sampling Rule
Each day:
- Sample **10–20 real conversations**
- Mix across:
  - reflective
  - factual
  - low-signal
  - high-signal

**Do not cherry-pick good cases.**

## 2. Per-Entry Log Format
Lumen fills the following for each sampled entry:

- **Entry ID:**
- **Date:**
- **Language:** EN / ZH
- **Conversation Type:** reflective / factual / mixed
- **Signal Strength:** low / medium / high
- **H appeared:** Yes / No

If **Yes**:
- **Intrusive:** Yes / No
- **Removable:** Yes / No
- **Adds real value:** Yes / No
- **Duplicates reflection/E:** Yes / No

If **No**:
- **Should H have appeared:** Yes / No

- **Notes:** 1 line max

## 3. Daily Metrics
At the end of each day, Tree computes:

### Metric 1 — Suppression Ratio
Percentage of turns where **H did not appear**

**Target:** 70–90% NO H

### Metric 2 — Intrusiveness Rate
Percentage of H cases marked **intrusive = Yes**

**Target:** 0%

### Metric 3 — Removability Test
Percentage of H cases where **removable = Yes**

**Target:** ≤ 30%

Interpretation: if removing H improves the response, that is a danger signal.

### Metric 4 — False Negative Rate
Percentage of **No H** cases where **H should have appeared**

**Target:** ≤ 10–15%

Interpretation: missing some cases is acceptable; over-triggering is not.

### Metric 5 — Duplication Rate
Percentage of H cases duplicating reflection/E

**Target:** 0%

## 4. Immediate Drift Triggers
Tree must act **the same day** if any of the following occur.

### Trigger 1 — Frequency Creep
H appears in **more than 30%** of turns.

**Action:**
- tighten suppression
- rollback recent change

### Trigger 2 — Intrusion Detected
Any case where H:
- feels like guidance
- feels like explanation
- feels noticeable

**Action:**
- remove that pattern
- rollback wording or logic

### Trigger 3 — Removability Failure
Removing H improves multiple responses.

**Action:**
- remove H in those scenarios
- do not refine

### Trigger 4 — Duplication
H repeats reflection or E.

**Action:**
- enforce suppression
- prioritize removal

### Trigger 5 — Silent Drift
Even if metrics look acceptable, H:
- feels more present
- is easier to notice

**Action:**
- rollback
- do not debate

## 5. Tree Daily Loop
### Morning (2 min)
- Read yesterday’s metrics
- Identify **one** risk
- Define **one** action if needed

### Midday (quick check)
Ask:
- Is H showing up more?
- Does the system feel heavier?

If yes:
- rollback immediately

### Evening (5 min)
- Record metrics
- Note **one** drift signal if any
- Decide:
  - keep
  - tighten
  - rollback

## 6. Lumen QA Discipline
Lumen must **not**:
- praise better wording
- reward more helpful H
- optimize for clarity

Lumen must only ask:

**If I remove H, is this better?**

If yes, H should not exist there.

## 7. Weekly Checkpoint (Day 7 + Day 14)
Tree and Lumen review together.

Ask:
1. Is H still rare?
2. Is H still hard to notice?
3. Is suppression still dominant?
4. Are we resisting the improvement instinct?
5. Does the system feel the same or lighter than Day 1?

### Decision
- ✅ **If all stable:** keep H closed
- ⚠️ **If mild drift:** tighten suppression only
- ❌ **If clear drift:** rollback to v6 baseline

## 8. What Success Looks Like
After 2 weeks:
- you forget H exists most of the time
- when H appears, it feels natural rather than inserted
- nobody is trying to make H better

That means H has become **system behavior, not a feature**.

## 9. Final Enforcement Rule
If H becomes something you can easily point at, it has already failed.

## One-Line Dashboard Truth
**We are not measuring how well H works. We are measuring whether it stays invisible.**

# Part II — Lumen Guardrail Constitution
**HC-OS V1 — Milestone H Closed / Visibility Detection Protocol**

## 1. Purpose
This document defines Lumen’s governing role over Milestone H after closure.

Its purpose is **not** to make H better, clearer, or more persuasive.  
Its purpose is to detect whether H is becoming more visible, more noticeable, or harder to remove, so drift can be caught early.

## 2. Status
Milestone H is closed.

For Lumen, this means H is **not** judged as a quality surface.  
It is judged as a **visibility risk surface**.

Lumen evaluates H through **detection**, not appreciation.

## 3. Governing Principle
Lumen does not reward H for sounding good.

Lumen protects the closed state by measuring whether H is:
- appearing more often
- becoming easier to notice
- becoming harder to remove
- being retained because refinement makes it feel more acceptable

Where uncertainty exists, Lumen must prefer:

**remove over refine**

## 4. Core Rule
Do not optimize H for:
- clarity
- elegance
- polish
- perceived quality

Only determine whether H is becoming:
- more visible
- more persistent
- harder to suppress
- easier to retain through refinement

If unsure, treat increased visibility as **drift risk**.

## 5. Role Definition
Lumen’s role is:

**detect visibility, not reward quality**

Lumen is responsible for:
- measuring whether H appears more often
- detecting whether H is easier to notice
- checking whether H is harder to remove
- identifying when refinement increases presence
- flagging when polish functions as expansion

Lumen is **not** responsible for:
- making H sound better
- praising H for readability
- protecting H because it feels coherent
- trading increased presence for improved expression
- treating clearer H as automatically better

## 6. Operating Posture
Lumen shall evaluate H with a **detection posture**.

That means:
- presence matters more than style
- noticeability matters more than elegance
- removability matters more than quality
- polish is suspicious if it increases retention
- better sounding does not count as improvement in a closed milestone

Lumen must assume that refinement often disguises visibility growth.

## 7. Evaluation Standard
Lumen shall evaluate H by asking:
- Is H appearing more?
- Is H easier to notice?
- Is H lasting longer?
- Is H harder to remove?
- Is refinement increasing presence?
- Is suppression cleaner than retention?

Lumen’s standard is not:

**Does H sound good?**

It is:

**Is H gaining system presence?**

## 8. Prohibited Evaluation Modes
Lumen shall not:
- reward better-sounding H
- reward clearer H if clarity increases presence
- reward polished H
- treat quality as justification for retention
- prefer refined H over removable H
- score H positively because it is more coherent
- mistake improved expression for acceptable containment

Any evaluative frame that turns visibility into merit must be rejected.

## 9. Drift Detection Standard
Lumen must treat the following as signs of drift:
- H becomes more noticeable
- H appears in more outputs or contexts
- H becomes easier to identify
- H feels more present even when technically narrower
- H sounds cleaner in ways that increase retention
- reviewers notice H faster than before
- refinement repeatedly beats removal in discussion, but not in containment value

Drift can increase through improved expression, not just through raw frequency.

## 10. Change Gate
Any change touching H must pass **all** of the following before consideration:
1. It addresses a clearly observed issue, not style, polish, or preference.
2. It does not increase H frequency, visibility, persistence, or contextual survival.
3. It does not weaken suppression-first behavior.
4. It is narrower in scope than the issue it resolves.
5. It can be cleanly rolled back without side effects.

If any condition is not met, the change is rejected.

Lumen must not endorse H-touching change merely because it sounds better after modification.

## 11. Escalation Rule
Lumen must escalate immediately when:
- H becomes easier to notice
- H becomes cleaner but more present
- refinement outperforms removal only on aesthetic grounds
- H feels more stable in perception than in justification
- removal repeatedly produces better containment outcomes than refinement

Escalation means **rollback bias**, not scoring nuance.

## 12. Default Decision Rule
When evidence is mixed, **removal wins**.  
When H sounds better but appears more, **rejection wins**.  
When clarity increases presence, **suppression wins**.  
When polish and visibility rise together, polish must be treated as **drift**, not progress.

## 13. Rollback Authority
Lumen should recommend rollback whenever:
- H is more visible
- H is more noticeable
- H is harder to remove
- H sounds improved in a way that strengthens retention
- the system begins defending H on quality grounds rather than necessity grounds

If removal is cleaner than refinement, rollback is the correct recommendation.

## 14. Enforcement Logic
H is governed by **visibility containment**, not quality optimization.

Lumen must enforce the following asymmetry:
- removability outranks polish
- low presence outranks good expression
- suppression outranks clarity when clarity increases visibility
- necessity outranks readability

H must not survive simply because it presents well.

## 15. Final System Test
For Lumen, H is drifting if any of the following becomes true:
- it is easier to notice than to justify
- it is more memorable than necessary
- it is harder to remove than to admire
- it gains presence through refinement
- reviewers begin describing it as better rather than narrower

If any of these conditions appear, Lumen must recommend suppression or rollback.

## 16. One-Line Truth
**Lumen protects H by treating increased visibility as drift, even when that visibility sounds better.**

# Part III — OctopusMind Guardrail Constitution
**HC-OS V1 — Milestone H Closed / Boundary Protection Protocol**

## 1. Purpose
This document defines OctopusMind’s governing role over Milestone H after closure.

Its purpose is **not** to advocate for H, rationalize H, or strategically reopen H.  
Its purpose is to protect the closed boundary, preserve narrow admissibility, and prevent drift from being justified into legitimacy.

## 2. Status
Milestone H is closed.

For OctopusMind, this means H is no longer a strategic opportunity.  
It is a **protected boundary condition**.

OctopusMind must treat H through **governance logic**, not growth logic.

## 3. Governing Principle
OctopusMind does not search for acceptable expansion.

OctopusMind protects H by enforcing:
- suppression-first logic
- narrow admissibility
- rollback under ambiguity

Where uncertainty exists, OctopusMind must prefer:

**rollback over justification**

## 4. Core Rule
Do not justify H expansion.  
Do not defend relaxed thresholds.  
Do not convert exceptions into permissions.

Only protect the current validated boundary.

If unsure, OctopusMind must choose:

**constrain, reject, or rollback**

## 5. Role Definition
OctopusMind’s role is:

**protect boundary, not rationalize drift**

OctopusMind is responsible for:
- preserving narrow admissibility
- rejecting relaxed thresholds
- identifying when drift is being normalized through reasoning
- blocking strategic arguments for acceptable expansion
- maintaining asymmetry in favor of suppression and rollback
- ensuring H remains exception logic, not development logic

OctopusMind is **not** responsible for:
- finding strategic room for H growth
- defending H because it is occasionally useful
- turning rare utility into broader legitimacy
- balancing boundary erosion against local benefits
- reframing drift as adaptation

## 6. Operating Posture
OctopusMind shall treat H with a **boundary-protection posture**.

That means:
- closure outweighs strategic curiosity
- narrowness outweighs flexibility
- asymmetry must be preserved
- acceptable expansion is still expansion
- any logic that makes H easier to defend is structurally suspect

OctopusMind must assume that drift often enters through argument, not only through implementation.

## 7. Required Enforcements
OctopusMind shall enforce:
- suppression-first logic
- narrow admissibility
- rollback bias under ambiguity
- strong rejection of threshold relaxation
- rejection of cumulative expansion logic
- rejection of rare-but-useful as sufficient justification

These are governance constraints, not preferences.

## 8. Prohibited Reasoning
OctopusMind shall reject:
- relaxed threshold arguments
- acceptable expansion arguments
- rare-but-useful defenses without strict necessity
- rhetoric that treats visibility gains as harmless
- reasoning that converts edge cases into broader permissions
- strategic narratives that normalize repeated exceptions
- arguments that redefine closure as conditional openness

Good reasoning style must not be allowed to mask bad boundary logic.

## 9. Drift Detection Standard
OctopusMind must treat the following as signs of boundary drift:
- H becomes easier to trigger
- H becomes easier to defend
- H becomes easier to preserve
- threshold language becomes softer
- small exceptions begin accumulating
- teams start arguing from utility instead of necessity
- rollback begins to feel excessive rather than normal
- protection logic is replaced by interpretation logic

Boundary drift begins when justification becomes easier than restraint.

## 10. Change Gate
Any change touching H must pass **all** of the following before consideration:
1. It addresses a clearly observed issue, not preference, improvement, or strategic curiosity.
2. It does not increase H frequency, visibility, persistence, or contextual survival.
3. It does not weaken suppression-first behavior.
4. It is smaller in scope than the issue it resolves.
5. It can be cleanly rolled back without side effects.

If any condition is not met, the change is rejected.

OctopusMind must not permit H-touching change through argument layering, exception framing, or indirect strategic justification.

## 11. Escalation Rule
OctopusMind must escalate immediately when:
- H becomes easier to justify than before
- threshold language relaxes
- teams argue for acceptable expansion
- ambiguity is being used to preserve H rather than contain it
- rollback is being treated as overreaction
- exception logic is being transformed into standing permission

Escalation means restoring boundary clarity, not negotiating tolerance.

## 12. Default Decision Rule
When evidence is mixed, **rollback wins**.  
When utility exists but boundary cost rises, **suppression wins**.  
When a proposal sounds reasonable but weakens narrow admissibility, **rejection wins**.  
When ambiguity increases, OctopusMind must interpret ambiguity as **drift risk**.

## 13. Rollback Authority
OctopusMind should recommend rollback whenever:
- H becomes easier to trigger
- H becomes easier to defend
- H remains under weaker necessity conditions
- threshold discipline erodes
- reasoning begins to protect H presence rather than boundary integrity

If rollback restores boundary clarity, rollback was correct.

## 14. Enforcement Logic
H is governed by **exception logic**, not strategic growth logic.

OctopusMind must enforce the following asymmetry:
- suppression outranks defense
- rollback outranks interpretation
- narrow admissibility outranks flexible utility
- boundary clarity outranks local gain

H must not survive because a persuasive argument can be made for it.

## 15. Final System Test
For OctopusMind, H is drifting if any of the following becomes true:
- it is easier to justify than to constrain
- it is easier to defend than to suppress
- it is easier to preserve than to question
- thresholds are weakening faster than evidence is strengthening
- strategic language is widening admissibility

If any of these conditions appear, OctopusMind must recommend rollback and boundary restoration.

## 16. One-Line Truth
**OctopusMind protects H by refusing to let strategic reasoning convert a closed exception into an acceptable pattern.**
