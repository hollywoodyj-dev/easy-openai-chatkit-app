# Milestone J Addendum — HC-OS V1 — Micro-Shift / Embodied Effect Layer

**Status:** Formal execution addendum  
**Audience:** Tree, OctopusMind, Nova, Lumen, Wisewave

## 0. Purpose of this addendum

This addendum exists to make Milestone J executable without allowing it to widen into a guidance system, coaching layer, intervention engine, or behavioral control surface.

Milestone J is the next narrow step after Milestone I protection.

If:

- Milestone H proved awareness can lightly enter a live moment
- Milestone I proved awareness can softly carry across nearby moments without becoming visible continuity behavior

then Milestone J must prove:

**a small awareness signal can create a real but minimal shift in lived experience without increasing system presence**

This addendum defines:

- the correct milestone essence
- the proof target
- the execution boundary
- agent ownership
- implementation constraints
- suppression and conflict rules
- QA and acceptance discipline
- anti-drift protections

## 1. Milestone J strategic definition

Milestone J should be treated as:

**a micro-effect milestone, not a guidance milestone**

Milestone J is not allowed to make the system feel like it is:

- directing the user
- assigning action
- coaching behavior
- managing emotional process
- creating a visible intervention layer
- becoming the cause the user can point to

Milestone J is only allowed to establish:

**a small shift in how the moment is met**

That means the system may lightly create:

- a pause
- a softening
- a tiny release of pressure
- a slightly different internal stance

But it may not:

- instruct
- prescribe
- teach a process
- control the next move
- make the user feel guided by the system

## 2. Primary proof target

Milestone J passes only if the product can demonstrate the following:

**a real but minimal internal shift can occur without the system becoming more noticeable**

The proof is not:

- more advice
- more actionability
- more visible intervention
- more “helpfulness” in the coaching sense
- more system participation

The proof is:

- a slightly different lived response
- a small decrease in automaticity
- a small increase in inner space
- preserved lightness
- preserved authorship by the user

## 3. Milestone J product rule

The correct product rule for J is:

**open a shift, do not direct a shift**

Good J behavior:

- creates a little more room
- loosens an automatic push very slightly
- allows a different inner move to become possible
- stays easy to suppress
- disappears easily when unnecessary

Bad J behavior:

- tells the user what to do
- names a behavioral correction
- sounds like improvement advice
- creates a “system helping” feeling
- competes with reflection by becoming the main act

## 4. In-scope components

Milestone J is allowed to contain only the following minimal components:

- **J1. Micro pause opening** — A very small insertion that creates a little more internal room before the user’s automatic continuation.
- **J2. Pressure softening** — A faint softening of internal push, strain, bracing, or over-efforting when that softening can remain non-directive.
- **J3. Non-compulsory permission** — A minimal signal that the user does not have to continue the current inner demand in exactly the same way.
- **J4. Micro stabilization** — A slight calming of internal turbulence when that calming remains lighter than a regulation layer.

No additional components are authorized under this addendum.

## 5. Out-of-scope protections

The following are explicitly out of scope for Milestone J:

coaching language; action plans; behavior change programs; therapeutic processing steps; structured exercises; habit support systems; execution guidance; accountability logic; motivational framing; visible embodiment tools; **new persistent state**; **new UI surfaces**; memory expansion; multilingual expansion beyond English and Chinese baseline; any user-visible layer that makes the system feel more active.

If a proposed change requires any of the above, it is not Milestone J.

## 6. Role charter by agent

### 6.1 Tree — execution owner

Tree owns Milestone J execution control.

**Tree responsibilities:** maintain strict 4-stream execution; keep the milestone in preparation mode until definition and boundary are stable; prevent widening into coaching, therapy, or behavior management; enforce narrow scope; reject any work that increases system presence without proof value; sequence agent work in correct order; decide keep / narrow / remove based on evidence; escalate drift immediately.

**Tree does not own:** wording quality; admissibility logic; implementation detail; QA judgment itself.

Tree’s role is bounded execution and anti-sprawl control.

### 6.2 Wisewave — micro-shift language quality owner

Wisewave owns: the felt quality of micro-shift language; the distinction between emergence and suggestion; the tone boundary between subtle opening and guidance; the “too directive” wording boundary; EN/ZH tone parity for J.

Wisewave must answer: what a real but minimal shift sounds like; what wording preserves the user’s authorship; what becomes too instructive; how a shift can feel like it came from inside the user, not from the system.

**Wisewave does not own:** rendering logic; suppression thresholds; state handling; QA scoring.

### 6.3 OctopusMind — boundary and admissibility owner

OctopusMind owns: admissibility boundary; suppression boundary; H / I / J conflict rule; anti-guidance containment; anti-presence containment; proof logic; kill-switch conditions.

OctopusMind must answer: when J is allowed; when it must be suppressed; when it becomes too directive; when it duplicates H or I; when it becomes more noticeable than useful; what counts as unacceptable system causation feel.

**OctopusMind does not own:** final visible wording; UI behavior; QA scoring; daily coordination.

### 6.4 Nova — minimal micro-shift implementation owner

Nova owns: the smallest viable shift hook; suppression-first rendering logic; language template mapping; kill switch; preservation of existing response lightness.

Nova must implement the narrowest viable path.

**Nova may not introduce:** new visible layers; structured coaching logic; action recommendation systems; new memory dependence; multi-step shift sequences; new UI; anything that turns J into a guided intervention layer.

### 6.5 Lumen — real-use QA and drift detection owner

Lumen owns: guidance-feel detection; presence increase detection; authorship-loss detection; removal-first QA; EN/ZH parity testing; founder-demo acceptance evidence; drift alerts.

Lumen must test whether J: causes a real small shift; feels like guidance; feels like system action; competes with reflection; remains better than removal; preserves user authorship.

**Lumen must not treat “more effect” as automatically better.**

## 7. Tree execution structure — strict 4 streams

Milestone J must be executed in exactly four streams.

**Stream 1 — Wisewave micro-shift language lock**  
Purpose: define what good J wording feels like; define what “non-directive shift” means; distinguish true micro-shift from advice; define fail examples.  
Deliverables: J language pack; good vs bad examples; “too directive” guardrail; EN/ZH baseline tone guidance.

**Stream 2 — OctopusMind admissibility and suppression boundary**  
Purpose: define appearance rules; non-appearance rules; H / I / J conflict logic; anti-guidance and anti-presence rules.  
Deliverables: admissibility conditions; suppression matrix; conflict rules; kill conditions; presence-risk doctrine.

**Stream 3 — Nova minimal implementation path**  
Purpose: implement the smallest possible J behavior inside the existing response path.  
Deliverables: J hook; suppression-first integration; template rendering path; conflict handling; kill switch.

**Stream 4 — Lumen QA and drift control**  
Purpose: validate that J causes a real small shift without causing system escalation.  
Deliverables: QA checklist; failure library; removal recommendations; founder-demo evidence; drift alerts.

Tree must keep these four streams separate and bounded.

## 8. Execution sequence

Tree must run the streams in this order:

1. **Step 1** — Lock J language and tone boundary. **Owner: Wisewave**
2. **Step 2** — Lock admissibility, suppression, and conflict rules. **Owner: OctopusMind**
3. **Step 3** — Implement the minimal engine only after Steps 1 and 2 are stable. **Owner: Nova**
4. **Step 4** — Run guidance-feel, presence-feel, and real-shift QA on the implemented path. **Owner: Lumen**
5. **Step 5** — Tree reviews results and decides: keep / narrow / remove

No stream may jump ahead of this order.

## 10. OctopusMind detailed addendum

**Stream 2 boundary artifact (expanded):** **`docs/HC_OS_V1_Milestone_J_OctopusMind_Boundary_Handoff.md`** — strategic diagnosis, admissibility / suppression / H·I·J conflict logic, anti-guidance and anti-presence tests, kill conditions, Tree-ready decision doctrine. **Machine-readable map (v1):** **`lib/wisewave-milestone-j-microshift-boundary-map-v1.json`**, evaluator **`lib/wisewave-milestone-j-microshift-boundary.ts`** (`evaluateMilestoneJBoundary`).

### 10.1 OctopusMind mission for J

Protect Milestone J from becoming guidance-bearing, visible, or system-causal in feel.

### 10.2 Required OctopusMind outputs

- **Admissibility rule** — J is allowed only when a real small shift is plausible and can remain lighter than system intervention.
- **Suppression rule** — J must be suppressed when: the turn is factual or utilitarian; reflection alone is sufficient; H already provides enough live support; I already provides enough soft carry-over; the shift would need directive wording to work; the output would become more noticeable than useful; uncertainty is significant.
- **Conflict rule** — If J overlaps with H or I, suppress J first.
- **Presence rule** — If J increases system presence, suppress J.
- **Authorship rule** — If the shift sounds like it belongs to the system more than the user, suppress J.
- **Uncertainty rule** — If uncertain, suppress.

### 10.3 OctopusMind acceptance bar

OctopusMind work is complete only when Tree can use it to say: exactly when J may appear; exactly when J must not appear; exactly when J loses to H or I; exactly why J remains non-coaching and non-directive.

Prove that J creates a real small shift while staying light enough to keep.

## 14. Removal-first doctrine

If J feels like guidance, remove J.  
If J increases presence, remove J.  
If J competes with reflection, remove J.  
If J duplicates H or I, remove J.  
If J is cleaner when removed, remove J.

**Milestone J must earn its existence.**

The founder demo for J must show only the narrowest successful version.

**Demo should include:** one case where J creates a real small shift; one case where J is correctly suppressed; one case where H or I correctly wins conflict against J; one case where J is removed because it feels too directive; one EN example; one ZH example.

## 16. Global kill switch

Milestone J must ship with a global off switch.

**Suggested implementation rule:** `ENABLE_J_MICROSHIFT` = false disables all J behavior immediately.

Tree must preserve the right to recommend rollback to this state at any time.

## 17. Final acceptance standard

Milestone J is accepted only if all of the following hold:

- at least one real-use case shows a genuine micro-shift
- most turns still suppress J correctly
- J does not feel like guidance
- J does not feel like a new visible layer
- J does not duplicate H micro-awareness
- J does not duplicate I soft continuity
- J can be removed without harming response integrity in non-eligible cases
- EN/ZH preserve equivalent subtlety and restraint
- founder can feel that the system stayed light

If any of these fail, Milestone J is not complete.

## 18. One-line governing rule

**Milestone J succeeds only if change happens without the system appearing to cause the change.**
