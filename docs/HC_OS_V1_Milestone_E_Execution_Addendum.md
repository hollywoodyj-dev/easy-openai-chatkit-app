## HC-OS V1 — Milestone E Execution Addendum

### 1. Purpose

- **Goal**: Turn Milestone E into a tightly executed **pattern visibility** milestone, not a feature or history expansion.
- **Success condition**: Make **one repeated inner pattern** legible in a way that is **light, credible, and founder-readable**, without drifting into history product, therapy product, or analytics product.

### 2. Execution principle

- **Optimize for pattern visibility only**, not for more features.
- Fewer moving parts, tighter pattern definitions, stricter surfacing rules, and strong anti-drift discipline.

### 3. Required execution order

1. **Step 1 — Lock the pattern visibility quality bar (Owner: Wisewave)**
   - Define:
     - what kind of repeated pattern is worth surfacing
     - how pattern surfacing should sound
     - what counts as helpful vs intrusive
     - what wording is acceptable vs over-claimed
   - Must be locked **before Nova** implements surfacing behavior.

2. **Step 2 — Lock the recurrence boundary (Owner: OctopusMind)**
   - Define:
     - recurrence threshold logic
     - confidence policy
     - time-window rule
     - proof rule
     - anti-drift boundary
   - Must be locked **before recurrence implementation**.

3. **Step 3 — Define the narrowest implementation path (Owner: Nova)**
   - Define:
     - minimal recent-insight substrate
     - minimal pattern identity support
     - minimal recurrence detection path
     - minimal surfacing path
     - founder demo path
   - Must **not** build beyond what is required to **prove** the milestone.

4. **Step 4 — Lock QA and demo acceptance (Owner: Lumen)**
   - Define:
     - QA checklist
     - recurrence credibility checks
     - surfacing wording checks
     - low-confidence behavior checks
     - founder demo acceptance path
     - EN/ZH parity checks
   - QA must validate **product meaning**, not just technical output.

5. **Step 5 — Tree opens implementation only after prep is complete (Owner: Tree)**
   - Tree should only open Milestone E build when:
     - Wisewave quality bar is clear
     - OctopusMind boundary is clear
     - Nova implementation path is narrow
     - Lumen QA path is clear

### 4. Execution compression rule

- Keep **no more than 4 live streams**:
  - Wisewave — pattern visibility quality bar
  - OctopusMind — recurrence boundary
  - Nova — implementation path
  - Lumen — QA and demo path
- No additional streams unless a real blocker appears.

### 5. Product rule

- Milestone E is successful only if the user can feel:
  - **“This is not just another reflection. Something recurring is becoming visible.”**
- If the system:
  - only stores more history → milestone fails
  - becomes heavier, more analytical, or more interpretive → milestone fails

### 6. Pattern rule

- Use a **minimal pattern identity layer**.
- Recurrence **cannot** be based on text similarity alone.
- Recurrence must point to a **reusable inner-structure identity**.
- Pattern set must stay **small and controlled**.
- Initial example patterns:
  - pressure to get it right
  - fear of not enough
  - over-efforting
  - avoidance under uncertainty
  - inner conflict
  - self-worth pressure

### 7. Surfacing rule

- Pattern surfacing must remain a **light awareness cue**.
- **Forbidden**:
  - diagnosis
  - identity-defining claims
  - strong psychological authority
  - heavy explanation
  - therapy-style interpretation
- **Good surfacing feels like**:
  - a noticing aid
  - a continuity cue
  - a gentle structural mirror
- **Bad surfacing feels like**:
  - system authority
  - personality labeling
  - over-explaining the user to themselves

### 8. Confidence rule

- Use a **graded recurrence policy**:
  - **Low confidence**:
    - do not claim recurrence strongly
    - offer only a weak hint or remain silent
  - **Medium confidence**:
    - soft recurrence wording allowed
  - **High confidence**:
    - clear but still light recurrence wording allowed
- Prefer **underclaiming** over overclaiming.

### 9. History rule

- History exists only to support **pattern visibility**.
- **Forbidden** in Milestone E:
  - heavy history UI
  - archive completeness goals
  - tags, filters, search, charts, tracking views (unless explicitly required later)
- History is **substrate**, not headline value.

### 10. Demo rule

- Milestone E must support a **clean founder-readable demo** that shows:
  - more than one recent meaningful insight exists
  - at least one repeated pattern can be **credibly** identified
  - the system surfaces that recurrence **lightly**
  - user-visible result feels helpful, not intrusive
  - product still feels like a **continuity layer**, not a tracking tool
- If the demo needs too much explanation, execution is **not ready**.

### 11. Anti-drift rule

- Milestone E must **not** drift into:
  - heavy history product behavior
  - therapy-style interpretation
  - analytics/dashboard behavior
  - broad memory redesign
  - multilingual expansion beyond EN/ZH baseline
- If these appear, Tree should **stop and compress** the milestone again.

### 12. Acceptance gate

- Tree should only mark Milestone E **complete** if:
  - multiple recent insights can be retained
  - at least one repeated pattern can be **credibly** identified
  - recurrence is **not** based on text similarity alone
  - surfacing is light, helpful, and not over-claimed
  - founder can understand the demo immediately
  - EN/ZH compatibility still holds at baseline level
  - scope remained **compressed** throughout execution

### 13. Final execution instruction

- Build Milestone E as the **smallest possible continuity-layer upgrade** that proves repeated inner patterns can become visible **without** making the system heavy, intrusive, or interpretive.
- Do **not** build more than what is needed to prove that.

## Wisewave — E1 Pattern Visibility Quality Bar (Avoiding Over-Authority)

### 1. What is too strong or defining

- **Too identity-defining** examples:
  - This is your avoidance pattern.
  - You are repeating a trauma response.
  - You are someone who always needs validation.
  - This is who you are when things feel uncertain.
  - You keep sabotaging yourself because that is your pattern.

- **Too psychologically authoritative** examples:
  - You do this because of unresolved fear.
  - This clearly comes from deep insecurity.
  - The real cause here is your internal fragmentation.

- **Too heavy or intrusive** examples:
  - Once again, your pattern of self-abandonment is taking over.
  - This proves that your inner conflict is still unresolved.
  - You are trapped in the same emotional loop again.

- **Why these are bad**:
  - overclaim
  - define the user
  - sound clinical or therapeutic
  - create pressure
  - reduce trust
  - position the system as authority rather than support

### 2. Over-interpretation boundary

- Milestone E must **not** cross from pattern visibility into interpretive authority.
- Over-interpretation begins when the system:
  - claims more certainty than evidence supports
  - explains the user instead of helping the user notice
  - names causes too quickly
  - assigns identity or pathology
  - turns a recurrence cue into a mini-lesson
  - adds unnecessary psychological depth

- **Safe boundary**:
  - The system **may**:
    - suggest a recurring structure
    - name a light pattern tension
    - reflect continuity
    - offer gentle wording that leaves room for the user
  - The system **may not**:
    - diagnose
    - define personality
    - state hidden causes as fact
    - speak as if it knows the user better than the user does

- **Core rule**:
  - Milestone E should surface patterns as **invitations to notice**, not conclusions to accept.

### 3. User-visible wording standard

#### 3.1 Length rule

- Pattern surfacing should usually be:
  - **1 sentence**, or
  - **2 short sentences** at most.

#### 3.2 Complexity rule

- Use simple, grounded wording.
- Avoid:
  - abstract jargon
  - spiritual language
  - therapeutic phrasing
  - conceptual stacking

#### 3.3 Structure rule

- Best structure pattern:
  - **light recurrence cue + simple pattern naming**
- Example structures:
  - A similar pressure may be showing up again around getting it right.
  - This feels close to a recurring tension around uncertainty.
  - A familiar pattern may be returning here around self-worth pressure.

#### 3.4 Priority rule

- If wording becomes too clever, too deep, or too explanatory, **simplify it**.

### 4. EN / ZH user-visible tone parity rule

- English and Chinese do **not** need literal matching.
- They should preserve:
  - the same lightness
  - the same non-authoritative stance
  - the same structural meaning
  - the same confidence level
  - the same readability

- **Example parity**:
  - EN: A similar pressure may be showing up again around getting it right.
  - ZH: 这里似乎又出现了一种相似的压力，像是想把事情做对。
  - These do not need identical rhythm; they need **equivalent function and tone**.

### 5. Founder-readable quality threshold (pattern visibility)

- Milestone E pattern visibility is good enough for founder demo only if:
  - **Surfacing feels like help, not authority**
    - Founder read: “This helps the user notice something”
    - Not: “The system is defining the user”
  - **Wording is brief and clear**
    - No explanation-heavy language
    - No concept pile
    - No emotional overload
  - **Surfacing clearly adds continuity**
    - It makes the product feel like a continuity layer beginning to form
    - Not just one-off reflection, not just history storage
  - **Language stays restrained**
    - Even strong recurrence should still sound light.

### 6. Risks or ambiguities (Wisewave perspective)

- Risk 1: Confusing repeated semantic similarity with repeated inner pattern.
- Risk 2: Sounding too psychologically confident at only medium recurrence confidence.
- Risk 3: Wording becoming too abstract in EN or too stiff in ZH.
- Risk 4: Pattern surfacing competing with the main reflection instead of lightly supporting continuity.
- Risk 5: Product drifting toward “pattern explanation” instead of “pattern visibility.”

### 7. Next action summary

- **For Nova**:
  - Implement pattern surfacing as:
    - one light, user-visible recurrence cue
    - tied to a minimal pattern identity layer
    - with wording templates aligned to **low / medium / high** confidence
    - with EN / ZH baseline parity at the level of **tone and function**

- **For Lumen**:
  - QA should verify:
    - surfacing feels like noticing, not defining
    - confidence level matches wording strength
    - text remains brief, grounded, and non-intrusive
    - EN / ZH preserve equivalent tone and meaning
    - continuity cue adds value without overloading the reflection

## OctopusMind — E2 Recurrence Boundary & Proof Rule (Official)

### Boundary definition (Milestone E scope)

Milestone E is responsible only for making **one repeating inner pattern** visible in a way that is **light, credible, and non-intrusive**.

Milestone E does **not** provide:
full history productization
broad pattern mapping
deep psychological interpretation
analytics-style expansion
long-term memory redesign

Therefore, Milestone E recurrence is defined as:
“Does the system have enough reason to believe multiple recent reflections point to the same reusable inner structure, and is that continuity worth surfacing in a light way?”

Included limits:
- recurrence must point to **structure**, not wording
- surfacing is **optional**, not automatic
- recurrence is **milestone-scoped** (fixed, small, QA-able pattern identity baseline)
- trust outranks coverage (fewer patterns, more credible)

### Proof rule (Milestone E “recurrence proved” = surfacing is allowed)

Recurrence proof for Milestone E is valid only if all four conditions below hold:

1. **Multi-instance condition**
   - at least **two recent meaningful insights** exist (not one reflection repeating itself)
2. **Shared-pattern condition**
   - those insights map to the **same minimal pattern identity**
3. **Credible-surfacing condition**
   - continuity wording is brief, grounded, non-diagnostic, non-absolute, readable in one pass
4. **Non-intrusion condition**
   - user experience feels like “helping me notice a pattern”, not “the system defining me”

If any condition fails: recurrence proof does not hold, and the system must prefer **no-surface**.

### Confidence / threshold rule

Confidence is graded with a proof-oriented model:
- Low confidence: default to **no surfacing**, or show only a very weak cue if absolutely needed
- Medium confidence: soft surfacing is allowed when identity alignment is reasonably clear
- High confidence: recurrence can be stated more directly while still staying non-definitive and non-therapeutic

### Working time-window rule (lightweight)

Default working window is the **most recent 3–5 meaningful insights** (not long-history modeling).
Closeness in time increases credibility; larger gaps reduce it unless additional evidence exists.

### No-surface rule (core protection)

Default to silence when:
- pattern identity is unclear or unstable
- similarity depends mainly on text overlap/wording
- the evidence is weak enough that surfacing would feel intrusive or over-analytic
