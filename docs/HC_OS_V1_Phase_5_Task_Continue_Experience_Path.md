# Phase 5 Task — Continue Experience Path

## Subject
Phase 5 — Continue Mechanism × User Journey Integration

## Audience
Tree / Nova / Wisewave

## Status
Next Phase

## Priority
High

## Phase Goal
Move Continue from a successfully fixed feature into a relied-on capability.

Phase 4 answered:

**What is Continue?**

Phase 5 must answer:

**Where, when, and how does Continue become genuinely valuable in the user journey?**

---

## 0. One-line phase definition

Phase 5 is not about redefining Continue.

Phase 5 is about making Continue behaviorally useful enough that users begin to rely on it.

---

## 1. Strategic context

Phase 4 is closed.

The system has already achieved:
- Thread → Continue object shift
- acceptable UI identity
- acceptable click feedback
- acceptable one-turn re-entry carry
- QA closure on the core mechanism

That means the central object-definition problem is no longer open.

The next challenge is different:

**A valid primitive is not yet the same as an adopted capability.**

Continue now works.

The next question is whether it becomes:
- noticed
- trusted
- reused
- behaviorally important

---

## 2. Core strategic question

**Under what user conditions does Continue most effectively reduce restart cost?**

This phase must determine:
- when Continue should appear
- when it should stay hidden
- what makes it feel worth using
- what causes it to be ignored
- what turns it from “nice” into “relied on”

---

## 3. Phase 5 objective

Design and validate the full Continue experience path.

This means understanding the user journey from:

**return → notice → interpret → select or ignore → send next input → receive resumed reply**

The goal is to make this path:
- low-friction
- intuitive
- repeatable
- habit-forming

---

## 4. What this phase is solving

Phase 4 solved:
- object ambiguity
- terminology drift
- dead click perception
- weak re-entry behavior

Phase 5 must solve:
- dependence formation
- trust formation
- placement logic
- appearance logic
- adoption logic

This is now a journey problem, not a definition problem.

---

## 5. Required outputs

Phase 5 should produce the following outputs:

### Output A — Continue 0–30 second user journey
Map the immediate experience path after a user returns.

Include:
- entry condition
- what the user sees
- what they infer
- what they click or ignore
- what they type next
- what the assistant does next
- what creates confidence or hesitation

### Output B — appearance logic
Define when Continue should appear, and when it should not.

This must include:
- strong-candidate cases
- weak-candidate cases
- no-candidate cases
- moments where surfacing Continue would add friction rather than reduce it

### Output C — dependence moments
Identify the highest-value moments for Continue.

Examples may include:
- unfinished emotional processing
- interrupted articulation
- partial reflection that was not resolved
- brief return to a recently active direction
- moments where restart burden is especially high

### Output D — adoption signals
Define how the team will know Continue is becoming a relied-on behavior.

Possible measures:
- repeat usage rate
- reduction in repeated context restatement
- faster time-to-next-meaningful-input
- stronger resumed-turn coherence
- user willingness to continue with short follow-up inputs

### Output E — drift guardrails
Define what must not happen in later expansion.

Continue must not drift into:
- history
- transcript retrieval
- visible memory layer
- summary list
- topic browser
- conceptual system object

## 7. Core investigation areas

### A. Return moments
Examine different kinds of return:
- immediate return after a short pause
- return after emotional interruption
- return after unresolved inner processing
- return after switching topics
- return after no strong unfinished direction exists

Question:

**Does Continue help equally across these, or only in specific cases?**

### B. Visibility economics
Continue is a low-visibility mechanism.

Question:

**How visible should it be before it becomes distracting, decorative, or over-present?**

The mechanism should not fight for attention.

It should appear when it reduces restart burden.

### C. Trust loop
Users will only rely on Continue if repeated experiences teach them that:
- it usually helps
- it does not confuse
- it saves effort
- it restores the right direction often enough

This trust loop must be explicitly examined.

### D. Ignore path
Continue does not need to be clicked every time.

Question:

**What does a healthy ignore pattern look like?**

A good system should allow:
- easy use when needed
- clean non-use when not needed

Success is not “everyone clicks it.”

Success is “it is valuable when present.”

---

## 8. Key design questions

Phase 5 must answer these clearly:
- What are the strongest moments for Continue to appear?
- What are the weak moments where it should stay hidden?
- What makes a user trust Continue after one successful use?
- What makes a user use it again later?
- What is the minimum cue needed for users to understand it without explanation?
- At what point would improving visibility start damaging lightness?
- What signals indicate that Continue is becoming a dependency rather than a novelty?

---

## 9. Constraints

### Do not do
- do not reopen Thread terminology debate
- do not redesign Continue as a visible system object
- do not add explanatory complexity
- do not expand it into history/memory/summaries
- do not optimize for feature visibility over user usefulness

### Stay focused on
- journey fit
- behavioral value
- trust formation
- restart-cost reduction
- low-friction repeatability
